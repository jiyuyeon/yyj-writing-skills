# 문서 작성 규칙 셀프 검사

가공 산출 문서를 저장하기 직전(또는 이미 저장된 문서를 점검할 때) 작성 규칙 위반을 grep으로 잡아내고, 위반마다 **고치는 법**까지 제시한다. 이 파일 하나로 자체 완결이다 — 프로젝트별 CLAUDE.md나 WRITING_RULES.md가 없어도 아래 원칙과 검사 항목 전체가 적용된다. 프로젝트 파일이 있으면 추가 규칙으로 얹는다.

## 적용 대상

- **검사함**: PRD, AC, Policy, 인터뷰 질문지, 페르소나, HMW, 가설표, 리서치, 요약, 회의록 등 **가공 산출물**
- **검사 안 함**: 비정제 원본(대화 메모, SNS 스크랩, 인터뷰 raw). 원형 보존이 목적이므로 규칙 미적용
- **예외**: 규칙·금지어를 *정의하는* 문장 자체에 금지어가 등장하는 것은 허용 (예: 이 SKILL.md, WRITING_RULES.md, agent 정의 본문)

## 글쓰기 원칙 (검사 전에 이대로 쓴다)

검사는 사후 안전망이고, 문서는 처음부터 아래 원칙대로 쓴다.

### 언어와 문체

- **언어 앵커링**: 모든 산출물은 현대 한국어 문어체로만 작성한다. 외부 자료(영어, 일본어)를 참고해 분석하더라도 최종 출력은 100% 한국어.
- **제안서체**: 표 밖 본문은 명사형 종결(수집, 측정, 필요, 불가, 완료)로 끊는다. `~한다`로 끝나는 서술 문장은 블로그체다.
- **라벨 콜론 형식**: `라벨: 내용, 상태, 담당`. 라벨 뒤도 명사형으로 압축한다. 한 라벨에 한 정보 — 정보가 둘이면 라벨을 쪼갠다.
- **과압축 경계**: 명사형으로 끊되 조사를 다 빼서 의미가 끊기면 안 된다. 읽어서 한 번에 이해되는 완결 어구까지만 압축.

### 구조

- **자체 코드 ID 금지**: 가설·페인포인트·축에 K1, X1, H4 같은 코드를 만들지 않는다. 이름으로 부른다(예: "시리즈 일관성 붕괴"). 정의 표를 넣어도 코드는 실패한다 — 독자가 표를 외워야 하기 때문. 다른 문서의 코드도 새 문서로 가져오지 않는다.
- **이 문서만 보고 이해되게**: 다른 문서를 봐야 뜻을 아는 표기(코드, 사내 전용 축약)를 쓰지 않는다. 개념은 처음 등장한 자리에 정의한다(항목 6·7 연동).
- **지지와 반증 병기**: 결론·근거 섹션에는 반대 방향 증거를 함께 싣는다. 못 찾았으면 "미발견"으로 명시한다(부재 증명 아님). 데이터가 없으면 "추가 확인 필요"라고 쓴다 — 수치·예산을 임의로 창작하지 않는다.

### 작업 절차

- **초안과 윤문 분리**: 구조와 내용을 먼저 확정하고 문체 정리는 별도 단계로. 한 번에 완성하려 하지 않는다.
- **verbatim 원칙**: 발화 인용, "그대로 가져오라"는 지시가 있는 원문은 오타까지 100% 보존. 윤문·검사 대상에서 제외.
- **humanize 계열 윤문 스킬 적용 범위**: 공고문·홍보문 등 읽히는 글 전용. 요청서·계획서·리서치 같은 산출 문서에 걸면 문체가 구어체로 풀려 이 스킬의 규칙을 위반하게 된다.

## 검사 대상 결정

1. 인자로 파일 경로가 주어지면 → 그 파일을 검사
2. 인자가 없으면 → 직전 턴에 작성·수정한 문서 본문을 검사
3. 둘 다 불명확하면 → 사용자에게 "어느 파일을 검사할까요?" 한 번 묻는다

## 검사 절차

대상 본문에 대해 아래 grep을 순서대로 실행한다. 한국어 매칭이므로 `grep -nE` 사용. 파일이면 파일 경로를, 본문이면 임시 검사한다.

### 1. 막연한 형용사·부사

```
grep -nE '풍부|크게|너무|매우|충분히|쉽게|간단히|상당히|적절히' <파일>
```

- 매칭 시: 수치·예시로 교체하거나, 근거가 같은 문단에 있는지 확인. (Show, Don't Tell)
- 예: "데이터가 풍부하다" → "공개 출처 4종 + 실거래가 API (2024 기준)"

### 2. 출처 없는 수치·비율

```
grep -nE '[0-9]+%|[0-9]+배|[0-9]{2,}만|[0-9]{2,}억' <파일>
```

- 매칭마다: 단위·기준일·출처가 **같은 줄**에 있는가 확인. 없으면 추가.
- 예: "80% 파악" → "80% 파악 (자체 추정, 검증 전. `가정:` 라벨)"

### 3. 단정어

```
grep -nE '당연히|명백히|확실히|반드시' <파일>
```

- 매칭 시: 근거가 같은 단락에 있는가? 출처가 1개뿐이면 단정형 금지.

### 4. 확증편향

- 자동 grep으로 안 잡힘 → **본문을 읽고** 판단:
  - 결론에 반대되는 증거를 최소 1개 적었는가?
  - 도메인 전문가 의견과 데이터를 같은 선상에 두지 않고 `데이터:` / `판단:` / `가정:` 라벨로 구분했는가?

### 5. 에세이형·질문형 제목 (명사구로)

```
grep -nE '이 문서가|할 것인가|왜 .*인가|어떤 .*있나|어떻게 .*나' <파일>
```

- 매칭 시: 명사구로 교체.
- 예: "이 문서가 답하려는 질문" → "개요" / "어떻게 받을 것인가" → "데이터 확보 방법"

### 6. 용어집 섹션 금지

```
grep -nE '^## 용어|용어집|용어 정리' <파일>
```

- 매칭 시: 용어집 섹션을 없애고, 약어·전문어를 **처음 나오는 자리에 괄호로** 설명.
- 예: "정부 허가(이하 라이선스: 받아야 하는 허가·등록, 자본금·심사가 따름)"

### 7. 풀어쓰지 않은 약어 (이 문서만 봐도 이해되게)

```
grep -nE '\bD[0-9]\b|MVP|불요|CPA|딥링크|후크|트리거|API|노선[AB]' <파일>
```

- 매칭 시: 첫 등장에 괄호 설명 추가, 또는 우리말로 풀어쓰기. ("불요" → "필요 없음")
- `MVP`처럼 흔한 약어도 첫 등장 1회는 풀어쓴다. (`MVP(최소 기능 제품)`)

### 8. 줄글 단락 (글머리기호로 분해)

- 자동 grep으로 안 잡힘 → **본문을 읽고** 판단:
  - 콜론 뒤 장문, `~한다`로 끝나는 풀어쓴 단락이 있으면 한 문장 한 메시지로 `-` 글머리기호 분해
  - 결론(BLUF) 자리에 요약표가 동반되는가? 글로만 결론 쓰면 안 됨
- **과압축 경계 (분해의 반대 실패)**: 개조식으로 줄이려다 조사·연결어를 다 빼서 의미가 끊기면 안 된다. 한 글머리는 읽어서 한 번에 이해되는 완결 어구여야 한다.
  - 나쁨: "직접 자본금 5억, 간접 비용 부담, 수동 입력 기반"
  - 좋음: "직접 수령은 자본금 5억이 들어 보류하고, 간접도 비용 부담이 커서 초기에는 사용자 수동 입력으로 받는다"
  - 한 글머리가 60자를 넘으면 의미 단위로 쪼개되, 쪼갠 조각마다 조사를 살려 문장이 끊기지 않게 한다.

### 9. 줄표(—) 남용

```
grep -noE '[가-힣A-Za-z0-9)] +— +[가-힣A-Za-z0-9(]' <파일>
```

- 줄표는 부연·근거를 본문에 잇는 한 가지 수단일 뿐. 다른 기호로 더 적합하면 그걸로 바꾼다.
- 대안: 라벨·항목 구분이면 `:`, 양자택일이면 `|`, 단순 나열이면 `-` 글머리기호, 경로·선택지면 `/`.
- 정말 "보충 설명을 한 호흡에 잇는" 경우에만 줄표를 남긴다.
- 예: "데이터 확보 — API로 받는다" → "데이터 확보: API로 받는다"

### 10. 가운뎃점(·) 남용

```
grep -noE '[가-힣A-Za-z0-9]·[가-힣A-Za-z0-9]' <파일>
```

- 가운뎃점은 긴밀히 묶인 대등 나열에만. 슬래시로 적합하면 `/`로 바꾼다.
- 예: "배경·목적·목표" (긴밀한 묶음 → 유지) / "아파트·상업용 중 택1" → "아파트/상업용 중 택1"

### 11. 마크다운 강조 별표 금지

```
grep -nE '\*\*' <파일>
```

- `**볼드**`는 쓰지 않는다. 별표가 본문에 삐져나오는 사고가 잦다.
- 강조는 표·제목·글머리기호 구조로 한다. 굳이 강조가 필요하면 따로 줄을 떼거나 라벨(`핵심:`)을 단다.
- 예: "`**핵심 결론**`" → 제목으로 올리거나 "핵심: ..." 라벨로.

### 12. 따옴표 남용

```
grep -noE '"[^"]{1,30}"|'"'"'[^'"'"']{1,30}'"'"'' <파일>
```

- 따옴표는 인용·정의·UI 문구 같이 꼭 구분해야 할 때만.
- 단순 강조·완곡 표현에 두른 따옴표는 뺀다.
- 예: "이른바 \"가능성\"이 보인다" → "가능성이 보인다" (강조용 따옴표 제거)

### 13. 군더더기·미사여구

- 자동 grep으로 안 잡힘 → **본문을 읽고** 판단. 빼도 의미가 그대로면 삭제한다.
- 후보: "~라고 할 수 있다", "~인 셈이다", "기본적으로", "사실상", "다양한", "여러 가지", "효과적으로", "성공적으로", "~에 대해서".
- 예: "기본적으로 다양한 데이터를 효과적으로 활용할 수 있다" → "데이터를 활용한다"

### 14. 표로 바꿀 나열 (표 vs 글머리 vs 줄글 기준)

- 자동 grep으로 안 잡힘 → **본문을 읽고** 판단. 기준은 비교 축(속성) 개수다.
  - **비교 축 2개 이상** (항목마다 비교할 속성이 둘 이상) → **표**. 예: 기능별로 "난이도 + 우선순위"를 같이 보면 표.
  - **비교 축 1개** (단일 기준의 나열) → **글머리기호**. 예: 확인할 항목 목록.
  - **이어지는 서술** (인과·흐름이 있는 설명) → **줄글**.
- 적용: 글머리기호로 늘어놓은 항목마다 `A: x, B: y` 식으로 속성이 2개 이상 반복되면 표로 바꾼다.
- **회의록·기획서의 큰 섹션도 표 대상이다.** 다음은 거의 항상 표로 바꿀 수 있다.
  - 핵심 결론(BLUF): `주제 / 결론 / 근거·비고` 3열
  - 의사결정·보류: `# / 결정(또는 열린 주제) / 근거·관점 / 상태` 4열
  - 주요 논의 요약: `주제 / 핵심 내용 / 근거·발언` 3열
  - 액션·후속: `# 또는 담당 / 할 일 / 기한·연결` 3~4열
  - 표의 한 칸이 또 여러 메시지를 담으면, 그 칸 안에서 글머리기호로 분해한다.

### 15. 풀어쓰지 않은 압축 라벨

```
grep -nE '데이터:|판단:|가정:|미검증|→ ?변호사|→ ?확인' <파일>
```

- 출처·검증 라벨을 약식 기호로 욱여넣으면 읽는 사람이 뜻을 모른다. 한국어 문장으로 풀어쓴다.
- 나쁨: "(데이터: 회의 중 발언, 미검증 → 변호사 확인 필요)"
- 좋음: "이 수치는 회의에서 나온 발언이며, 사실 여부는 변호사 확인이 필요하다."
- `데이터:` / `판단:` / `가정:` 라벨 자체는 사실·의견 분리(규칙 4)를 위해 쓰되, 뒤에 오는 검증 상태는 문장으로 설명한다.

### 16. 남탓·평가·대립 표현 (중립으로)

```
grep -nE '논쟁|충돌|미해소|미결|합의.{0,3}못|엇갈|정정|틀렸|틀린|잘못|착오|오류|괴리|대립|정답 없음' <파일>
```

- 회의에서 의견이 갈린 것을 다툼·실수처럼 적지 않는다. 아이데이션은 여러 관점이 나오는 자리다.
- 누가 틀렸다는 뉘앙스(엇갈림·정정·틀림·착오)는 지운다. 이번에 확인된 사실만 남긴다.
- 대립어 → 중립어
  - "논쟁 / 충돌했다" → "방향을 논의했다 / 관점이 나뉘었다"
  - "미해소 / 미결 / 합의 못 함" → "이어서 논의 / 다음에 결정"
  - "갈린 의견" → "나온 관점"
  - "괴리감" → "거리감이 있어 보인다"
  - "1차 회의의 엇갈림을 정정한 셈이다" → (삭제하고 이번에 확인된 내용만 기록)
- 의견 주체("정상진은 / 최용욱은")는 남겨 누구 관점인지 보이게 하되, 대립 프레임은 쓰지 않는다.

### 17. 이유 누락 · 브리핑/할 일 혼동

- 자동 grep으로 안 잡힘 → **본문을 읽고** 판단.
- **이유 누락**: 발언·결론을 옮길 때 "왜 그런지"를 빠뜨리지 않는다.
  - 나쁨: "거짓 입력은 본인 손해다."
  - 좋음: "거짓으로 입력하면 자기에게 안 맞는 추천을 받게 되어 본인이 손해다."
- **브리핑/할 일 혼동**: 회의에서 누가 발표·공유한 것(브리핑)을 액션 리스트(앞으로 할 일)에 넣지 않는다. 액션에는 회의에서 담당·기한이 정해진 것만 적는다.

### 18. docx 표 물리 서식 (python-docx로 만들 때)

- 줄글이 아니라 워드 표를 만들 때 적용. 아래가 빠지면 표가 답답하고 좌측 여백이 과하게 넓어 보인다.
- **라벨 열 너비**: 자동 균등분할(기본값)을 끄고 라벨 열을 글자폭에 맞게 좁힌다. `cell.width`만으로는 안 먹으니 `tblGrid`를 직접 다시 쓰고, `tblLayout`을 fixed로 둔다(중복 제거).
- **셀 여백**: `tblCellMar` 상하 약 70 twips, 좌우 약 110 twips.
- **줄간격·단락 간격**: 셀 문단 줄간격 약 1.12, 본문 문단 줄간격 1.15에 단락 후 4pt.
- **세로 정렬**: 셀 세로 가운데(`WD_ALIGN_VERTICAL.CENTER`)로 짧은 칸과 긴 칸의 높이를 맞춘다.
- **칸 안 분해**: 한 칸이 여러 메시지면 셀 안에서 글머리기호(`-`)로 나눈다.

### 19. AI 입장·내부 표현 노출 금지 (읽는 사람 입장으로)

```
grep -nE '[A-Za-z0-9_./-]+\.(md|txt|docx|csv|json|py|html)|이 ?(저장소|레포|리포지토리|디렉터리|폴더)|어디에 저장|저장 ?위치|새 ?파일|커밋|경로:|파일명:' <파일>
```

- 산출 문서는 읽는 사람(유연지·협업자)을 위한 것이지, AI의 작업 메모가 아니다. AI가 어디에 무엇을 저장하는지는 문서 본문에 넣지 않는다.
- 매칭 시: 내부 파일경로·저장 절차·시스템 용어를 지운다. 자료를 가리켜야 하면 사람이 아는 이름으로 풀어 쓴다.
  - 나쁨: "어디에 저장: `research/competitor_analysis.md` (이 저장소 안에 새 파일)"
  - 나쁨: "`research/competitor_analysis.md` 참고"
  - 좋음: "경쟁 서비스 분석 결과 (별도 문서로 정리)" — 읽는 사람이 무슨 문서인지 알게 풀어 쓰고, 실제 경로는 문서 밖(대화·전달 메시지)에서 안내.
- 판단 기준: "이 문장이 사용자에게 의미가 있나, 아니면 AI의 작업 진행 상황인가." 후자면 본문에서 뺀다.

### 20. 일기체·푸념·날것 사연 금지 (담백한 공식 문서로)

- 자동 grep 일부 + **본문을 읽고** 판단. 산출 문서는 공식 기록이다. 진행 중 감정·하소연·날것의 사연을 일기 쓰듯 적지 않는다.
- 사실로 확정되지 않은 진행 상태를 완료·진행형으로 단정하지 않는다. 아직 안 한 일을 "하는 중/했다"로 쓰면 날조다.

```
grep -nE '진행 ?중|진행하고 있|완료했|끝냈|~하고 있다|손이 부족|여력이 없|바빠서|짜치|어쩔 수 없이|아쉽게도|다행히|~느라' <파일>
```

- 매칭 시 두 가지로 나눠 고친다.
  - 사실 단정(진행 중/완료): 실제 상태가 맞는지 확인. 안 했으면 계획형으로. "인터뷰 10명 진행 중" → "인터뷰 10명 예정 (2026-05-26~06-30, 아직 미시작)".
  - 감정·사연·푸념: 동기로서 의미가 있으면 담백한 한 줄로 옮기고, 아니면 뺀다. "리서치 손이 부족해서 어쩔 수 없이" → 배경에 "리서치 인력이 1명이라, 조사 일부를 자동화로 보완한다"로.
- 단, 일을 하는 진짜 이유(동기)는 빼지 말고 살린다. 사용자가 "이걸 하는 이유"라고 말한 핵심 동기가 배경·목적에서 누락되면 안 된다. 푸념은 덜어내되 이유는 남긴다.

### 21. 사용자 제약 무시 금지 (예산·인력·범위)

- 자동 grep으로 안 잡힘 → **본문을 읽고** 판단. 사용자가 못 박은 제약(예산 0, 인력 부족, 자산 범위 등)과 어긋나는 방법을 제안하지 않는다.
- 비용·유료·구독·결제를 전제로 까는 방법이 있으면, 사용자가 그 비용을 쓸 수 있다고 했는지 확인. 안 했으면 무료·대체 방법으로 바꾸거나 `가정:` 라벨로 비용을 명시해 사용자가 판단하게 한다.
  - 나쁨: (예산 없다고 한 상황에서) "경쟁 서비스를 직접 구독해 사용 후 분석한다"
  - 좋음: "경쟁 서비스는 공개 자료(웹/리뷰/무료 체험)로 분석한다. 유료 구독이 필요하면 비용을 먼저 확인한다(`가정:` 라벨)."

### 22. 번역투·AI 상투구 (영어 직역 패턴)

```
grep -nE '되어지|되어질|보여진다|불리운다|에 있어서?|를 통해|을 통해|으로 인한|로 인한|으로 인해|로 인해|시사하는 바|귀추가 주목|주목된다|아닐 수 없다|한 배를 탔|결론적으로|더욱이|나아가|그럼에도 불구하고' <파일>
```

- 영어의 수동태·전치사·상투 결론을 한국어로 1대1 치환한 번역투. 발견 즉시 교체한다.
- 교체 방향:
  - 사물 주어 피동("작성되어질") → 행위자 능동·명사형("작성 예정")
  - "~에 있어서" → "~에서" / "~를 통해" → "~로" / "~로 인한" → "~때문에"
  - "시사하는 바가 크다", "귀추가 주목된다" → 삭제하고 액션 아이템이나 후속 결정 과제로 종료
  - 접속사 연발("결론적으로", "더욱이", "나아가") → 생략하고 문맥·어미로 연결
- 예외: 발화 인용문·verbatim 원문 안의 번역투는 보존 (원형 보존 원칙 우선).
- 주의: "~를 통해"는 실제 경유 의미(예: "결제는 앱을 통해서만 가능")면 유지 가능. 수단·방법의 관용적 사용만 교정.
- 260804 클로드 한국어 글쓰기 향상법 조사 반영으로 추가.

### 23. 서술체 종결 (제안서체 강제)

```
grep -nE '^[^|#>\-].*(한다|된다|이다|있다|없다|간다|본다|쓴다|뺀다|넘긴다)\.?$' <파일>
```

- 표 밖 본문 줄이 서술체 종결어미로 끝나면 블로그체다. 산출 문서는 제안서체: 명사형 종결(수집, 측정, 필요, 불가, 완료)로 끊는다.
- 라벨을 붙였어도 뒤가 서술체면 위반. "채택 방식: ~에서만 가져온다" → "창작자가 실제 쓴 글에서 근거 수집".
- 한 라벨에 한 정보. 같은 말을 여러 문장으로 반복하면 요지가 사라진다.
- 예외: 회의록의 발언 인용, CLAUDE.md 같은 지침 문서, 이 스킬 파일 자체.
- 260804 사용자 직접 수정 예문 기반으로 추가. 예문은 이 파일 상단 "퓨샷 예문" 표 참조.

### 24. 자체 코드 ID (다른 문서를 봐야 아는 표기)

```
grep -nE '\b[A-Z][0-9]{1,2}[a-d]?\b' <파일>
```

- 가설·페인포인트·축·항목에 붙인 자체 코드(K1, X1, H4, Q1a 등)가 본문에 있으면 위반. 이름으로 교체한다.
- 매칭 판단: H1이 HTML 헤딩·규격명 등 실제 고유명사면 통과. 문서가 스스로 만든 분류 코드면 위반.
- 정의 표가 같은 문서에 있어도 위반이다 — 독자가 표를 외운 상태로 뒤 섹션을 읽어야 하기 때문.
- todo 관리 파일(O01 같은 내부 트래킹 라벨)은 산출 문서가 아니므로 예외.
- 260804 사용자 지시("이 문서만 보고 알 수 있게 하라")로 추가.
